# Бэкенд: лидерборды, чат и онлайн-бой на Nakama

Документ описывает серверную часть проекта — что развёрнуто, как это настроено
и какие ограничения у текущего решения. Онлайн-бой разобран в разделе
[Онлайн-бой](#5-онлайн-бой).

Одиночные режимы (игрок против игрока за одной клавиатурой, против бота и рейд
на босса) остаются **отдельными режимами** и работают без сервера.

---

## 1. Что это даёт игроку

- **Общий чат** с сохранением истории. Сообщения переживают перезагрузку страницы
  и видны всем, кто зайдёт позже — история подтягивается с сервера при открытии чата.
- **Таблица лидеров** по числу побед, в двух разрезах: за всё время и за неделю
  (недельная сбрасывается по понедельникам).
- **Ник**, который виден в чате и в таблице. Аккаунт привязан к браузеру
  (device ID в `localStorage`), логин/пароль не нужны.
- **Онлайн-бой 1 на 1** по коду комнаты — см. раздел [Онлайн-бой](#5-онлайн-бой).

Победа засчитывается **по одной за выигранный бой**:

| Режим | Засчитывается | Почему |
|---|---|---|
| Игрок против бота, победил игрок | да (`kind: bot`) | понятно, кому принадлежит победа |
| Рейд на Гига-Босса под управлением ИИ, победил герой | да (`kind: boss`) | то же самое |
| Онлайн-бой, любая сторона | да (`kind: pvp`) | у каждого свой аккаунт; записывает только победитель |
| Локальный бой двух игроков за одной клавиатурой | **нет** | оба сидят под одним аккаунтом, победа никому конкретно не принадлежит |
| Босс под управлением игрока | **нет** | режим симметричный, привязка к аккаунту бессмысленна |

Если сервер недоступен, игра работает как раньше — просто без чата и таблицы.
Это заложено намеренно: сетевой слой нигде не является обязательным.

## 2. Эксплуатация: что и где развёрнуто

### Схема

```
Браузер (GitHub Pages, https)
        │  https://dev.gritsenko.biz/game_api/...
        ▼
   nginx на 192.168.1.12  ──── Let's Encrypt, автопродление через systemd-таймер
        │  proxy_pass → 127.0.0.1:7350 (префикс /game_api срезается)
        ▼
   Nakama 3.41.0 (docker)  ──►  PostgreSQL 16 (docker, том nakama_pgdata)
```

### Файлы на сервере

| Путь | Что это |
|---|---|
| `/opt/nakama/docker-compose.yml` | описание сервисов, копия — в репозитории: `server/nakama/docker-compose.yml` |
| `/opt/nakama/.env` | секреты (`chmod 600`, только root). В репозиторий не попадает |
| `/opt/nakama/modules/leaderboards.lua` | серверный модуль, копия — `server/nakama/modules/leaderboards.lua` |
| `/etc/nginx/sites-available/dev.gritsenko.biz` | внешний https-вход |
| `/etc/nginx/sites-available/lan-game-api` | тот же прокси по http для локальной сети |

Порты Nakama (7350 API, 7351 консоль) слушают **только `127.0.0.1`** — наружу
попасть можно исключительно через nginx.

На роутере достаточно проброса **80 и 443**. Отдельный порт для WebSocket не
нужен: соединение начинается обычным HTTP-запросом на 443 с заголовком
`Upgrade: websocket` и апгрейдится прямо в нём. Со стороны nginx за это отвечают
`proxy_http_version 1.1`, заголовки `Upgrade`/`Connection` и увеличенные
таймауты, чтобы игровой сокет не рвался на долгих боях. Порт 80 нужен для
выпуска и продления сертификата (проверка HTTP-01) и редиректа на https.

### Проверка после перезагрузки

Контейнеры и nginx подняты в автозапуске (`restart: unless-stopped` и
`systemctl enable`), поэтому после ребута сервер встаёт сам. Убедиться, что он
именно **работает**, а не просто «процессы запущены»:

```bash
ssh 192.168.1.12 /opt/nakama/healthcheck.sh
```

Скрипт (копия — `server/nakama/healthcheck.sh`) проверяет службы, здоровье
контейнеров, авторизацию, подъём WebSocket, доступность лидерборда и срок
сертификата. Возвращает ненулевой код, если что-то не так, — годится для cron
или мониторинга. Пробный аккаунт, который он создаёт, тут же удаляется.

### Типовые команды

```bash
ssh 192.168.1.12
cd /opt/nakama

sudo docker compose ps                    # состояние
sudo docker compose logs -f nakama        # логи
sudo docker compose restart nakama        # перечитать leaderboards.lua после правки
sudo docker compose up -d                 # применить изменения compose-файла
```

Обновление серверного модуля из репозитория:

```bash
scp server/nakama/modules/leaderboards.lua 192.168.1.12:/tmp/
ssh 192.168.1.12 'sudo mv /tmp/leaderboards.lua /opt/nakama/modules/ && cd /opt/nakama && sudo docker compose restart nakama'
```

### Админ-консоль Nakama

Наружу она **не выставлена** и выставлять её не нужно — сервер активно сканируют
боты (в `/var/log/nginx/error.log` видно запросы к `/.env`, `/wp-json` и подобному).
Доступ через SSH-туннель:

```bash
ssh -L 7351:127.0.0.1:7351 192.168.1.12
# затем открыть http://localhost:7351, логин admin
# пароль: sudo grep NAKAMA_CONSOLE_PASSWORD /opt/nakama/.env
```

## 3. Техническая часть

### Модули клиента

| Файл | Назначение |
|---|---|
| `src/net/config.ts` | адрес сервера, идентификаторы лидербордов, имя комнаты чата |
| `src/net/client.ts` | сессия, устройство, ник, переподключение, статус сети |
| `src/net/chat.ts` | вход в канал, история, отправка и приём сообщений |
| `src/net/leaderboard.ts` | запись победы через RPC и чтение таблиц |
| `src/scenes/socialScene.ts` | весь DOM и обработчики; транспорта здесь нет |
| `server/nakama/modules/leaderboards.lua` | создание лидербордов и RPC `record_win` |

Разделение намеренное: `src/net/*` ничего не знает о DOM, `socialScene.ts` — о сети
ровно столько, сколько нужно для отрисовки.

### Переменные сборки

Задаются через `.env.local` локально (см. `.env.example`) и через GitHub Actions
при деплое. Все они попадают в клиентский бандл, поэтому **секретов среди них нет**.

| Переменная | Значение по умолчанию | Смысл |
|---|---|---|
| `VITE_NAKAMA_HOST` | `dev.gritsenko.biz` | хост Nakama |
| `VITE_NAKAMA_PORT` | `443/game_api` | порт **вместе с путём прокси**, см. ниже |
| `VITE_NAKAMA_SSL` | `true` | https/wss или http/ws |
| `VITE_NAKAMA_SERVER_KEY` | — | `socket.server_key` сервера |
| `VITE_NAKAMA_DEV_PROXY` | — | только для `vite dev`, см. ниже |

В CI они подставляются в шаге `Build` (`.github/workflows/static.yml`):
`VITE_NAKAMA_SERVER_KEY` берётся из **secrets**, остальные — из **variables**.
Если ключ не задан, сборка пройдёт, но игра соберётся без сетевых функций.

> Значение ключа можно посмотреть на сервере:
> `sudo grep NAKAMA_SERVER_KEY /opt/nakama/.env`

### Разработка: бэкенд через dev-сервер

`vite dev` по умолчанию ходит на тот же `dev.gritsenko.biz`, что и собранная
игра. Изнутри домашней сети это работает нестабильно: внешний адрес возвращается
через роутер (hairpin NAT) и отвечает примерно через раз, отчего подключение
выглядит зависшим.

Поэтому есть `VITE_NAKAMA_DEV_PROXY`. Если переменная задана, Vite поднимает
прокси `/game_api` → указанный адрес (`vite.config.ts`), а клиент в dev-режиме
ходит на собственный origin — `src/net/config.ts` подменяет `host`/`port`/`useSSL`
значениями из `location`. В бой это не попадает: проверка идёт по `import.meta.env.DEV`.

```
VITE_NAKAMA_DEV_PROXY=http://192.168.1.12     # дома: мимо hairpin NAT
VITE_NAKAMA_DEV_PROXY=https://dev.gritsenko.biz  # снаружи
```

Что это чинит помимо hairpin:

- страница открыта по `http://localhost:5173`, а бэкенд по `https` — со стороны
  браузера схемы больше не смешиваются;
- запросы становятся same-origin, то есть без CORS и preflight;
- dev-сервер, открытый с телефона (`http://192.168.1.5:5173`), работает без
  отдельной настройки — адрес берётся из `location`.

Сокет идёт по тому же пути, поэтому в описании прокси обязателен `ws: true` —
иначе `/game_api/ws` не апгрейдится.

Проверить, что прокси поднялся:

```bash
curl -i http://localhost:5173/game_api/healthcheck   # 200 и заголовок server: nginx
```

> Если в ответ прилетает **404**, дело почти всегда в потерянном префиксе
> `/game_api`: такого location у nginx нет. Стоит посмотреть в DevTools полный
> URL запроса — он должен быть вида `.../game_api/v2/...`.

### Почему путь прокси приклеен к порту

`nakama-js` не умеет базовый путь. Внутри клиента URL собирается простой
конкатенацией — `${scheme}${host}:${port}` для HTTP API и `${scheme}${host}:${port}/ws`
для сокета. Поэтому `port = "443/game_api"` даёт корректные
`https://dev.gritsenko.biz:443/game_api/v2/...` и `wss://.../game_api/ws`.

Это трюк, и он может сломаться при обновлении `nakama-js`. Если бэкенд когда-нибудь
переедет на отдельный поддомен (`game.gritsenko.biz`), `port` станет обычным `443`,
и трюк можно будет убрать.

### Ник и технический логин — почему их два

В Nakama `username` уникален и лежит в JWT. При этом `nakama-js` 2.8.0 разбирает
токен как `JSON.parse(atob(payload))`: `atob` возвращает байтовую строку, поэтому
**любой не-ASCII `username` ломает разбор** с ошибкой
`Bad control character in string literal in JSON`. Для игры с русскими никами это
означает, что ник не может быть `username`.

Поэтому их два:

- `username` — технический, вида `u<deviceId без дефисов>`, только ASCII,
  игроку никогда не показывается;
- `display_name` — человеческий ник, кириллица разрешена; в JWT не попадает.

Следствия, о которых надо помнить:

- В чате имя автора передаётся **внутри сообщения** (`{ text, name }`), потому что
  `ChannelMessage.username` — технический. В истории это исторический снимок имени
  на момент отправки: если игрок сменил ник, старые сообщения останутся со старым.
- В лидерборд имя пишет сервер: RPC берёт `display_name` через `nk.users_get_id`.
- **Nakama не проверяет `display_name` на уникальность** — два игрока могут взять
  одинаковый ник. Если это станет проблемой, лечится отдельной коллекцией-индексом
  в storage и проверкой в RPC при смене имени.

### Защита счёта

Лидерборды созданы **authoritative**: прямую запись счёта клиентом Nakama отклоняет
(`Leaderboard only allows authoritative score submissions`). Единственный путь —
RPC `record_win`, который всегда прибавляет ровно `1`, а величину задаёт сервер,
а не клиент.

Полной защиты это не даёт и дать не может: браузер — недоверенная среда, и никто
не мешает вызвать RPC в цикле из консоли. Порог поднят (нельзя одной записью
поставить себе 9999), но если накрутки станут проблемой, следующий шаг — лимит
вызовов на пользователя в единицу времени внутри того же RPC.

### Ввод с клавиатуры

`game.ts` вешает глобальный `keydown` с `preventDefault()` на все клавиши. Это
запретило бы печатать в чате, поэтому обработчик пропускает события, у которых
фокус находится в `INPUT`, `TEXTAREA` или `contenteditable` (функция `isTextEntry`).
Любое новое текстовое поле на странице автоматически попадает под это правило.

## 4. Известные ограничения

| Ограничение | Последствие | Что делать |
|---|---|---|
| Hairpin NAT на роутере | Из домашней сети обращение к `dev.gritsenko.biz` проходит примерно через раз (замеряно: 5 успешных TCP-соединений из 10 против 10 из 10 напрямую по `192.168.1.12`). Снаружи проблемы нет | См. «Hairpin NAT» ниже |
| Аккаунт привязан к браузеру | Очистка данных сайта = новый аккаунт и потеря побед | При необходимости добавить вход по email или ссылку-восстановление |
| `display_name` не уникален | Возможны одинаковые ники | Индекс в storage + проверка в RPC |
| Накрутка побед через RPC | Теоретически возможна | Лимит вызовов в RPC |
| 1 CPU / 2 ГБ RAM на сервере | Для игры с друзьями достаточно, но запас невелик | Следить за `docker stats` при росте нагрузки |

### Hairpin NAT: почему дома связь рвётся

Устройство из домашней сети обращается к `dev.gritsenko.biz`, то есть на внешний
IP. Пакет уходит на роутер, и тот должен развернуть его обратно внутрь сети —
это и называется NAT loopback (hairpin). Многие домашние роутеры делают это
ненадёжно, поэтому соединения устанавливаются через раз. Сам сервер при этом
простаивает: в логах нет ни ошибок, ни следов неудачных попыток — TCP-соединение
до него просто не доходит.

Проверить, что дело именно в этом:

```bash
# через внешний адрес
for i in $(seq 1 10); do timeout 4 bash -c 'echo > /dev/tcp/dev.gritsenko.biz/443'   && echo ok || echo fail; done
# напрямую по локальному
for i in $(seq 1 10); do timeout 4 bash -c 'echo > /dev/tcp/192.168.1.12/443'   && echo ok || echo fail; done
```

Если первый список рваный, а второй полностью `ok` — это роутер.

Варианты решения, от лучшего к простому:

1. **Split-horizon DNS на роутере.** Добавить запись, по которой внутри сети
   `dev.gritsenko.biz` резолвится в `192.168.1.12`. Тогда все домашние устройства
   ходят напрямую, минуя петлю. Работает и в браузере, и в дев-сборке, менять в
   проекте ничего не нужно. Если дома стоит AdGuard Home, Pi-hole или dnsmasq —
   это одна строка.
2. **Запись в hosts на конкретной машине:** `192.168.1.12  dev.gritsenko.biz`.
   TLS при этом остаётся валидным — сертификат выписан на это имя, а nginx
   отдаёт нужный server-блок по SNI. Минус: уехав из дома, запись надо убрать.
3. **Локальный адрес в `.env.local`** (`VITE_NAKAMA_HOST=192.168.1.12`,
   `VITE_NAKAMA_PORT=80/game_api`, `VITE_NAKAMA_SSL=false`) — годится только для
   `npm run dev`, на задеплоенный сайт не влияет.

Независимо от роутера клиент теперь переживает единичный сбой сам: после
неудачной попытки подключение повторяется через секунду с ростом паузы, а
возврат сети или переход на вкладку запускают попытку немедленно.

## 5. Онлайн-бой

### Как это выглядит для игрока

На экране выбора бойцов у второго игрока появился режим **Онлайн** рядом с
«Игрок / Бот / Босс». Одиночные режимы работают ровно как раньше и сервер им не нужен.

1. Выбираешь своего бойца (сетку соперника режим прячет — он выбирает сам).
2. **Создать бой** — получаешь код из 5 символов и передаёшь другу.
3. Друг выбирает своего бойца, вводит код и жмёт **Войти**.
4. Бой начинается сразу у обоих.

Создавший бой всегда слева, вошедший — справа. Клавиши у обоих одинаковые
(`WASD`, `F`, `G`, `R`), переучиваться между режимами не нужно.

Победа в онлайн-бою идёт в таблицу лидеров как `kind: pvp` — её записывает
только выигравшая сторона.

### Модель синхронизации

**Host-authoritative.** Бой целиком считает создатель комнаты (хост):

```
    Гость                                   Хост
 ввод (30/сек)  ──── OP_INPUT ────────►  applyRemoteInput() → обычная симуляция
 предсказание                                      │
 локально                  ◄──── OP_STATE ─────────┘  снимок 20/сек
```

Почему так, а не lockstep/rollback как в настоящих файтингах: игровое ядро
недетерминировано. Цикл в `src/game.ts` работает с плавающим `dt`
(`Math.min((timestamp - lastTime) / 1000, 0.05)`), а `Math.random()` вызывается
прямо в боевой логике. Host-authoritative обходится без переписывания ядра —
хост просто продолжает считать бой как в одиночной игре.

Расплата — **задержка ввода у гостя равна пингу**. Режим рассчитан на игру
между близко расположенными игроками; на 150 мс файтинг разваливается.
Перевод на детерминированную симуляцию с rollback остаётся возможным позже:
он потребует фиксированного шага, сидированного PRNG и разделения
`simulate()` / `draw()`.

Чтобы управление не ощущалось вязким, гость **предсказывает** свои действия
локально: крутит `Fighter.update()` своего бойца каждый кадр, а снимок хоста
подтягивает его к авторитетной позиции мягко (35% к цели за пакет). Расхождение
больше 60 px защёлкивается сразу: это уже не дрейф предсказания, а рассинхрон.

**Чужой боец идёт через буфер интерполяции** (`RemoteFighterBuffer` в
`sync.ts`). Снимки приходят 20 раз в секунду, а рисуем мы 60: если защёлкивать
позицию по приходу пакета, чужой боец дёргается — визуально это читается как
«у него 20 fps». Вместо этого снимки копятся в буфере, а боец рисуется в
прошлом — на `INTERP_DELAY_MS` (100 мс) назад, смешиванием двух соседних
снимков. Между пакетами всегда есть куда двигаться, а дрожание сети съедается
запасом буфера. Своей симуляции у чужого бойца при этом нет: `update()` ему не
крутится, иначе он уезжал бы от авторитетного состояния.

Что смешивается, а что нет:

| Поля | Как |
|---|---|
| `x`, `y`, `vx`, `vy`, `displayHp`, таймеры, `animFrame` | линейно между снимками |
| `hp`, `combo` | ступенькой — по ним ловится момент попадания |
| `facing`, `grounded`, `attacking`, `attackType` | ступенькой — дискретные по смыслу |

Расхождение больше 80 px между соседними снимками — это не сеть, а респавн на
новом раунде: туда телепортируем. Если пакеты пропали, позиция досчитывается по
скорости не дольше 120 мс, потом боец замирает — лучше замереть, чем уехать в стену.

Плата за буфер — постоянные 100 мс задержки отрисовки соперника. Управление это
не ухудшает: свой боец предсказан локально, а попадания всё равно считает хост.

Гость **не считает** попадания, урон и конец раунда — иначе события применились
бы дважды. Искры при попадании он рисует по факту падения HP в снимке.

### Кириллица в пакетах

`nakama-js` кодирует тело пакета через `btoa`, а тот умеет только Latin-1.
Любой не-ASCII символ в полезной нагрузке (например `koText = 'РАУНД 1'`) ронял
отправку с `InvalidCharacterError` — причём внутри промиса, мимо `try/catch`,
так что снимки молча переставали доходить. Поэтому `match.ts` перед отправкой
экранирует всё за пределами ASCII в `\uXXXX`: это по-прежнему валидный JSON, и
`JSON.parse` на той стороне возвращает исходную строку.

### Комнаты без серверного кода

Nakama умеет именованные матчи: `createMatch(name)` делает детерминированный
match id из имени, поэтому обе стороны попадают в один матч, вызвав его с
одинаковым именем. Код комнаты и есть имя матча (`mk67-<КОД>`) — отдельное
хранилище кодов и RPC не нужны.

Алфавит кода не содержит `0`, `O`, `1` и `I`: их путают на слух и на вид.
Совпадение кодов теоретически возможно, поэтому хост проверяет, что созданная
комната пуста, и при необходимости берёт новый код.

### Модули

| Файл | Назначение |
|---|---|
| `src/net/match.ts` | транспорт: комнаты, коды, приём и отправка пакетов |
| `src/net/sync.ts` | формат пакетов: какие поля бойца летят по сети и как применяются |
| `src/scenes/onlineScene.ts` | UI комнаты, связка транспорта с игровым ядром |
| `src/game.ts` | ветки хоста и гостя в игровом цикле |

`game.ts` публикует точки входа через `window` (`startOnlineFight`,
`onRemoteInput`, `onRemoteState`, `onOpponentLeft`) — так же, как остальные
экранные функции. DOM живёт в сцене, симуляция в ядре.

### Ограничения режима

| Ограничение | Причина |
|---|---|
| Пауза не останавливает бой | Симуляция идёт у хоста и ждать не станет. Меню паузы открывается, чтобы можно было выйти |
| «Реванш» создаёт новую комнату | Матч закрывается при выходе с экрана победы |
| Босс-файт только одиночный | Онлайн — 1 на 1 обычными бойцами |
| Если хост вышел, бой закончился | Передачи роли хоста нет |
| Подбор случайного соперника | Не сделан: комнаты только по коду. Матчмейкер Nakama можно добавить поверх |
